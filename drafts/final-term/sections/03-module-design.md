# 模块设计

## 3.1 模块划分原则

在总体架构基础上，系统模块设计以“职责单一、契约稳定、可替换、可审计”为原则。由于蛋白质设计任务具有长链路、高成本和易失败的特点，模块划分不能仅按前后端或代码目录机械拆分，而应围绕任务生命周期中的关键行为组织：任务如何进入系统，计划如何产生，步骤如何执行，风险如何发现，失败如何恢复，结果如何汇总，审计信息如何保存。

因此，本系统可划分为七类主要模块：任务接入与交互模块、规划与候选生成模块、自适应工作流规划与恢复模块、工作流执行模块、工具适配与能力管理模块、安全与质量门禁模块、存储审计与结果汇总模块。它们共同支撑从自然语言目标到最终报告的闭环。

## 3.2 任务接入与交互模块

任务接入与交互模块负责将用户意图转化为系统可执行任务，并在关键节点向用户呈现可决策信息。该模块在实现上主要对应 FastAPI 接口、React 工作台、Task Builder、Pending Review Workspace、Decision Form、事件时间线和能力 readiness 面板。

该模块的输入可以是自然语言 `goal`、自由文本 `query` 或已经确认的 `ConfirmedTaskSpec`。系统首先创建任务草稿或意图草稿，允许用户补充缺失字段，再通过确认接口生成正式任务。相比直接提交 JSON，这种设计更符合科研任务的实际特点：用户最初往往给出的是目标和约束的混合描述，系统需要在执行前完成字段收敛、场景门控和工具能力预览。

交互模块的另一项职责是承载人在环路。任务进入 `WAITING_PLAN_CONFIRM`、`WAITING_PATCH_CONFIRM` 或 `WAITING_REPLAN_CONFIRM` 后，模块需要展示候选数量、默认建议、候选摘要、成本风险、运行时状态摘要和解释依据。用户提交的 Decision 通过 API 写回后端，并由 Decision Apply 模块应用到工作流。该模块不应越权修改计划或执行工具，而是作为人类决策与后端 FSM 之间的受控接口。

## 3.3 规划与候选生成模块

规划与候选生成模块以 PlannerAgent 为中心，负责从任务目标和约束生成可执行候选。该模块依赖 ProteinToolKG、工具 readiness、任务约束、预算策略和已完成步骤上下文，输出 `PlanCandidate`、`PatchCandidate` 或 `ReplanCandidate`。当前实现中，候选生成逻辑进一步拆分为 candidate_generator 的模型、过滤、构造和排序逻辑，以减少 Planner 主体中的耦合。

初始规划时，Planner 根据任务类型和能力提示选择相应阶段能力，例如序列探索、结构映射、质量门禁、结构条件精修和目标评分。每个候选都需要转换为结构化 payload，通常是 `Plan` 或 `PlanPatch`，并附带 `candidate_id`、`summary`、`score_breakdown`、`risk_level`、`cost_estimate`、`explanation` 和 `source_refs`。候选集合通过 Top-K 形式输出，便于自动选择或人工确认。

候选生成模块的关键约束是硬可行性过滤。工具必须存在于 registry 或知识图谱中，步骤输入必须能由任务约束或前置步骤输出解析，安全等级不能越界，预算硬约束不能突破。过滤后的候选再进入评分和排序。评分不只考虑目标贴合度，还需要考虑可执行性、风险、成本、置信度、工具 readiness 和工具覆盖度。该设计保证 Planner 生成的是可执行工作流候选，而不是仅在文本上合理的建议。

## 3.4 自适应工作流规划与恢复模块

自适应工作流规划与恢复模块是 CEBRA-WP 的工程承载模块，也是本课题区别于固定流水线系统的核心。该模块贯穿规划、执行和恢复过程，主要包括 RuntimeState 更新、runtime adjustment、action utility 计算、动作选择、patch/replan 候选生成和 terminal stop 候选构造。

RuntimeState 是该模块的关键状态对象。它以轻量级 belief-state 表示运行时隐含状态，字段包括成功概率、结构失败概率、恢复余量、预期剩余成本、证据充分性、预算压力和最后更新来源。该状态由 StepResult、SafetyResult、失败上下文、已完成步骤数和预算上限等观测更新，并可写入 TaskSnapshot 或候选 metadata。它不是新的 Agent，也不拥有任务状态；它只为 Planner 和 Workflow 提供可解释的运行时摘要。

运行时调整用于把静态候选评分转化为证据感知排序。若当前结构失败概率升高、预算压力增大或恢复余量降低，高成本候选的最终得分会受到抑制；若证据充分性较高且候选具备较好恢复路径，则候选可能获得正向调整。实现侧将该逻辑封装为 `compute_runtime_delta`、`RuntimeEvaluator` 和相关 metadata 字段，包括 `runtime_adjustment`、`shadow_score`、`final_score`、`rerank_reason` 和 `action_utility`。

动作选择模块把算法动作映射到系统恢复闭环。`continue` 表示继续当前计划；`patch_local` 表示保留计划前缀并生成局部修补；`suffix_replan` 表示替换未执行后缀或重新选择后续工具链；`stop` 表示当前后续投入不再合理，应作为终止型 replan 候选等待确认。动作选择会结合阶段触发矩阵、失败类型、失败码、重试是否耗尽、安全阻断和运行时状态摘要。这样，系统可以在高代价结构预测或目标评分失败时做出比“简单重跑”更细粒度的恢复判断。

该模块与 HITL 的关系也需要明确。CEBRA-WP 可以推荐默认候选和动作，但在需要人工确认的场景下，它只提供候选与解释；是否应用 patch、replan 或 stop 由 Decision 决定。该边界保证了算法建议的可审查性。

## 3.5 工作流执行模块

工作流执行模块负责将已确认的计划推进为实际计算过程。其主要实现对象包括 Workflow、PlanRunner、StepRunner、ExecutorAgent、状态迁移工具和错误分类模块。

ExecutorAgent 的直接输入是 `Plan` 和 `WorkflowContext`。PlanRunner 负责完整计划的执行生命周期，包括从 `PLANNED` 到 `RUNNING`、再到 `SUMMARIZING` 的状态推进；StepRunner 负责单个步骤的输入解析、适配器调用和 StepResult 构造。执行过程中，系统需要维护 `WorkflowContext` 中的计划、步骤结果、安全事件、设计结果、当前状态和待决策对象。

步骤执行的核心是引用解析和结果归一化。PlanStep 可以直接包含字面值，也可以引用上游步骤输出，例如 `S1.sequence` 或 `S2.pdb_path`。StepRunner 需要在执行前解析这些引用，若引用不存在或类型不匹配，应产生可诊断错误。工具执行成功后，模块将输出、指标、产物路径和调用元数据写入 StepResult；执行失败时，模块记录失败类型、错误信息、错误细节和重试上下文，为后续 patch/replan 提供证据。

工作流执行模块还承担高代价阶段的局部控制。例如结构映射阶段可以对多个序列候选进行批量结构投影，并在主工具失败时尝试 fallback 工具；结构精修阶段可以根据迭代结果判断是否继续；质量门禁阶段可以聚合拒绝原因并触发相应恢复路径。这些逻辑仍应保持在 Executor/Workflow 边界内，不应侵入 Planner 的候选生成职责。

## 3.6 工具适配与能力管理模块

工具适配与能力管理模块负责把外部生物信息学工具、远程模型服务和本地分析脚本包装为统一能力。该模块由 `BaseToolAdapter`、`AdapterRegistry`、具体适配器、ProteinToolKG、active tool metadata 和 readiness 检查共同组成。

`BaseToolAdapter` 定义所有适配器需要遵循的基本接口：`resolve_inputs` 将 PlanStep 和上下文转换为工具实际输入；`run_local` 执行本地工具；`run_remote` 支持远程服务；`describe_capabilities` 暴露工具身份、适配器身份和执行模式；`healthcheck` 检查依赖是否可用；`normalize_error` 将异常转为统一结构；`estimate_cost` 和 `estimate_latency` 提供成本与耗时估计。具体工具只需实现这些接口，Executor 即可通过统一入口调用。

AdapterRegistry 维护 tool_id 和 adapter_id 到适配器实例的映射，避免执行层硬编码工具类。ProteinToolKG 则从规划视角描述工具能力，包括 capability、输入输出、兼容关系、成本、安全等级和版本。二者分工不同：Registry 面向运行时调用，ToolKG 面向规划与约束推理。readiness 模块进一步提供工具可用、降级或不可用状态，使 Planner 在生成候选时能考虑当前环境，而不是只依据静态工具目录。

当前实现中的适配器覆盖了序列生成、结构预测、质量控制、目标评分和可视化等能力。对于需要外部服务的模型，适配器会记录 provider、endpoint type、remote job id 等元数据，以便恢复和审计。

## 3.7 安全与质量门禁模块

安全与质量门禁模块用于控制系统输出边界并减少无效高代价调用。该模块包括 SafetyAgent、RiskFlag、SafetyResult、quality gate 以及若干阶段特定检查逻辑。

SafetyAgent 的职责是对输入、步骤和输出阶段进行风险判定。其输出包含风险等级、风险代码、消息、作用范围、步骤编号和细节字段。当安全结果为 `warn` 时，系统可以记录告警并视策略继续；当结果为 `block` 时，应触发 replan 或等待人工确认，而不是由 SafetyAgent 直接终止任务。这样既保留了安全信号的强约束作用，也避免 SafetyAgent 越权承担计划修改职责。

质量门禁更偏向工程与数据质量控制，主要检查序列合法性、结构完整性、低复杂度、指标缺失、结构置信度不足等问题。它与 SafetyAgent 的关系是互补的：质量门禁可以产生步骤级失败或过滤原因，SafetyAgent 则从风险治理角度给出是否允许继续的结论。在 de novo 六阶段工作流中，质量门禁位于低成本证据积累与高代价调用之间，能够帮助系统尽早过滤明显不可用候选。

## 3.8 存储、日志、快照与结果汇总模块

存储与审计模块为系统的可追溯和可恢复提供基础。任务记录 `TaskRecord` 保存对外状态、内部状态、目标、约束、计划、设计结果、当前 PendingAction、决策列表和安全事件。事件日志记录状态迁移、待决策创建、工具调用、失败恢复和用户决策。快照保存任务上下文、计划版本、已完成步骤、运行时状态摘要和待决策信息。

进入任意等待状态前，系统必须先写入 PendingAction、事件日志和 TaskSnapshot。这一顺序是恢复能力的关键：如果系统在等待用户期间重启，后端可以从快照恢复到完整的等待场景；如果系统在执行中断，也可以根据已完成步骤和远程作业上下文恢复执行或提示人工处理。

结果汇总模块由 SummarizerAgent 承担。它在任务进入 `SUMMARIZING` 后读取上下文，生成 `DesignResult`，其中包括候选序列、结构路径、评分、风险标记、报告路径和元数据。报告生成强调可读性和审计性，应体现任务目标、计划与重规划记录、关键指标和安全信息，但不能把机制验证夸大为生物学最终结论。

## 3.9 模块协作流程

一次典型任务的模块协作过程如下。用户首先通过任务接入模块提交目标并确认约束，系统生成 `ProteinDesignTask`。规划模块读取任务和 ToolKG，生成 Top-K Plan 候选；若需要人工确认，交互模块展示 PendingAction，用户提交 Decision。确认后的 Plan 进入工作流执行模块，Executor 按步骤调用工具适配器并产生 StepResult。安全与质量门禁模块对关键输入和输出进行检查，并将风险事件写入上下文。

如果某一步成功，RuntimeState 根据观测更新，工作流继续推进；如果某一步失败且可重试，执行模块优先重试；若重试耗尽或质量门禁失败，自适应恢复模块根据失败上下文和运行时状态选择 patch 或 replan 路径。Planner 生成相应候选，系统进入等待确认。用户接受后，Decision Apply 模块应用候选，Workflow 从快照恢复并继续执行。最终所有步骤完成后，Summarizer 汇总结果，任务进入 `DONE`。

## 3.10 模块设计小结

本系统的模块设计将蛋白质设计工作流拆解为可契约化、可恢复和可审计的若干职责单元。任务接入模块保证输入规范化，规划模块保证候选可执行，自适应恢复模块保证运行时决策具备证据基础，执行模块保证工具调用与状态推进，适配模块保证外部能力可替换，安全与质量门禁模块保证风险边界，存储与汇总模块保证结果可追溯。通过这些模块的协作，系统能够在保持软件工程边界清晰的同时，将 CEBRA-WP 算法自然嵌入 de novo 蛋白质设计工作流。

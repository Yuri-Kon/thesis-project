# 需求分析

## 1.1 背景与问题界定

蛋白质设计任务通常不是单一模型调用可以完成的孤立计算，而是由目标描述、候选序列生成、结构预测、质量筛选、目标评分、结果汇总等环节共同构成的长链路科研工作流。不同工具在输入输出格式、运行成本、失败模式和适用边界上存在明显差异：序列生成工具能够给出候选空间，结构预测工具能够提供折叠置信度，质量控制与目标评分工具则负责过滤不可用结果并支持排序。若仅依赖固定流水线，系统很难在运行中根据中间证据调整后续步骤，也难以在高代价工具失败或结果质量不足时保留已有有效前缀并进行局部修复。

本课题面向 de novo 蛋白质设计场景，研究并实现一个面向高代价科研工作流的智能规划与执行系统。系统的核心目标不是替代具体生物学模型本身，而是在多个蛋白质设计与分析工具之间建立可组合、可执行、可追溯的工作流控制机制。用户以自然语言目标和结构化约束描述任务，系统将任务转化为统一的数据契约，基于工具知识图谱生成候选计划，在执行过程中记录中间结果与运行状态，并在失败、风险或目标偏离时触发重试、局部修补、后缀重规划或终止建议。

因此，本系统的需求应同时覆盖软件工程层面的任务管理、接口交互、状态持久化和可观测性，也覆盖算法层面的候选计划生成、可行性过滤、运行时状态估计与恢复决策。二者并非并列割裂关系：CEBRA-WP 算法提供的是工作流控制层的决策逻辑，而 Web/API、FSM、Agent 和工具适配器则为该算法提供可执行、可审计的工程载体。

## 1.2 用户与使用场景

系统的主要使用者可概括为两类。第一类是需要提交蛋白质设计任务并审查关键决策的科研人员。他们关注任务目标是否被正确理解、工具链是否合理、候选方案的风险和成本是否可接受，以及最终结果是否包含足够的序列、结构、指标和审计信息。第二类是系统开发与实验人员。他们关注工具接入是否规范、工作流失败是否可定位、不同恢复策略是否可复现实验，以及算法消融和系统验证所需的日志、快照和运行指标是否完整。

围绕上述使用者，系统需要支持以下典型场景。其一，用户提交一个自然语言蛋白质设计目标，并补充长度范围、安全等级、结构模板、预算等约束，系统自动生成结构化任务和候选计划。其二，在初始计划包含高成本或高风险工具时，系统暂停在人工确认状态，向用户展示 Top-K 候选、默认建议、风险等级、成本估计和解释信息。其三，执行过程中某一步工具失败、返回结果不满足 schema、质量门禁全部拒绝或结构预测置信度不足时，系统能够根据失败上下文生成 patch 或 replan 候选，而不是直接宣告任务失败。其四，在任务运行完成后，系统生成面向阅读和复核的报告，并保留事件日志、快照、决策记录和中间产物路径，以支持后续审计与实验复现。

## 1.3 功能性需求

### 1.3.1 任务接入与约束确认

系统应提供统一的任务接入能力，将自由文本目标收敛为 `ProteinDesignTask` 及其结构化约束。任务接入过程需要支持自然语言目标、显式约束和任务元数据，并能够在信息不足时保留待补充字段。实现侧已包含 Task Intake、Intent Draft、场景门控和确认接口，说明任务创建并非简单表单提交，而是一个由草稿、补充、确认到正式任务的渐进过程。

任务接入模块至少应满足以下要求：

1. 为每个任务生成唯一 `task_id`，记录目标、约束、创建时间和元数据。
2. 将自然语言输入、结构化约束和确认后的任务规格统一投影到任务契约。
3. 在正式执行前进行场景可行性和工具能力 readiness 预览，避免明显不可执行任务直接进入工作流。
4. 保持任务创建过程可追溯，尤其是用户补充、系统推断和最终确认之间的关系。

### 1.3.2 候选计划生成与工具链选择

系统需要根据任务目标、约束和 ProteinToolKG 中的工具能力信息生成候选计划。候选计划不应仅包含工具名称，还应包含步骤依赖、输入引用、输出字段、风险等级、成本估计和解释说明。计划的最小执行单元是 `PlanStep`，多个步骤共同构成 `Plan`；步骤之间通过 `"Sx.field"` 形式表达中间结果引用。

候选生成阶段需满足硬可行性要求：工具必须存在，输入输出必须闭合，schema 必须合法，安全等级与预算约束不得被突破，关键工具应具备可用性信息。对于未触犯硬约束但证据不足或能力降级的候选，系统可以保留为 `degraded_feasible`，但应要求人工确认或明确策略授权，不能在无保护条件下静默执行。

### 1.3.3 工作流执行与工具适配

系统应能够按照已确认的 `Plan` 调用具体工具，并将每一步的执行结果收敛为统一的 `StepResult`。工具调用通过 ToolAdapter 完成，Executor 只依赖适配器注册表和抽象接口，而不直接绑定具体工具内部实现。当前实现中已包含 ESMFold、OpenFold、ProteinMPNN、ProtGPT2、RDKitProps、DSSP、Foldseek、BLASTP、MMseqs2、Objective Ranker 等适配器或相关执行封装，能够支撑不同阶段能力的组合。

执行模块应支持：

1. 解析步骤输入，包括常量输入和上游步骤输出引用。
2. 统一记录工具身份、适配器身份、执行模式、远程作业 ID、错误类型、指标和产物路径。
3. 对步骤失败进行分类，区分可重试错误、不可重试错误、工具错误、安全阻断和质量门禁失败。
4. 在局部失败时优先遵循 `retry -> patch -> replan` 的恢复顺序。
5. 允许 Nextflow 等后端作为单步工具执行边界，但多步控制流仍由 Workflow/FSM/Plan 负责。

### 1.3.4 人在环路与决策审查

蛋白质设计工作流中存在高风险、高成本和高不确定性的节点，系统不能把所有关键选择都交给自动逻辑。因此，系统需要显式支持人在环路机制。人在环路不应表现为 Agent 直接等待用户或绕过状态机的临时输入，而应通过 `PendingAction` 和 `Decision` 两个结构化对象完成。

系统至少需要支持三类人工确认：初始计划确认、局部 patch 确认和整体 replan 确认。进入任一 `WAITING_*` 状态前，系统必须先持久化候选集合、默认建议、解释信息和任务快照。用户提交决策后，系统根据决策类型应用对应的 Plan、PlanPatch 或 Replan，并记录决策事件。对于算法建议的 `stop`，其语义应作为终止型 replan 候选呈现；用户接受后任务进入失败终态，主动取消则对应 `CANCELLED`。

### 1.3.5 运行时自适应与恢复决策

普通固定流程只能在设计前确定工具链，无法充分利用执行过程中的失败码、质量指标、预算消耗和安全信号。本系统需要在运行时维护轻量级状态估计，即 Lite belief-state / `RuntimeState`，用于描述当前任务继续执行的成功概率、结构失败概率、恢复余量、预期剩余成本、证据充分性和预算压力。

在此基础上，CEBRA-WP 需要支持四类运行时动作：`continue`、`patch_local`、`suffix_replan` 和 `stop`。动作选择不应只依赖某一步是否失败，而应综合阶段、失败类型、重试是否耗尽、安全是否阻断、运行时状态摘要和候选 utility。该需求直接服务于高代价步骤治理：在结构预测、结构条件精修或重型目标评分之前，系统应尽量利用低成本证据减少无效调用；在高代价步骤失败后，系统应优先判断是否能够保留前缀并进行局部修补。

### 1.3.6 结果汇总、报告与审计

系统最终输出不仅是某个单一序列或结构文件，还应包括任务目标、计划版本、步骤结果、结构与质量指标、安全事件、恢复轨迹和报告路径。Summarizer 应在任务进入汇总阶段后启动，负责生成面向用户阅读的 `DesignResult` 和报告文本。即使报告生成失败，也不应反向改变已经形成的执行结果有效性。

同时，系统需要保留审计链路：`PendingAction -> Decision -> EventLog -> TaskSnapshot`。事件日志用于描述状态变化、候选生成、决策提交、工具执行和恢复动作；快照用于支持中断后的上下文恢复。对于长时间运行任务和远程模型调用，该要求是系统可靠性的基础。

## 1.4 非功能性需求

系统应具备可追溯性。任何计划生成、候选推荐、人工确认、状态迁移和恢复动作都应能从日志或快照中追踪其依据。算法输出中的 `source_refs`、`score_breakdown`、`runtime_adjustment`、`action_utility` 等字段，均服务于解释与复核。

系统应具备可扩展性。新的蛋白质设计或分析工具应通过 ToolAdapter 接入，并在 ProteinToolKG 中声明能力、输入输出、成本、风险和可用性信息。Executor 不应因新增具体工具而改变核心调度逻辑。

系统应具备可靠性与可恢复性。任务状态迁移必须受 FSM 约束，进入等待状态前必须完成快照写入，系统重启后能够根据最新快照和事件日志恢复执行上下文。对于远程模型和高代价工具，系统需要记录远程作业上下文和恢复提示。

系统应具备安全与边界控制能力。SafetyAgent 负责输入、步骤和输出阶段的风险判定，但不直接决定终止或重规划；其输出应作为 FSM 和 Planner 的触发信号。系统不得把补充性机制验证扩大为最终生物效果结论，也不得将未验证指标写成已完成实验结论。

系统应具备实验可复现性。论文实验需要比较静态单链、静态门控、动态观测和完整 Lite belief-state 等策略，因此实现需要稳定记录 runtime policy、候选得分、动作 utility、高代价调用次数、恢复成功情况和最终任务状态。

## 1.5 需求小结

综上，本系统的需求可以概括为：面向 de novo 蛋白质设计的多工具链路，构建一个以统一任务契约为入口、以 FSM 为控制骨架、以多 Agent 为职责划分、以 ToolAdapter 为外部能力接入方式、以 CEBRA-WP 为运行时规划与恢复核心的智能工作流系统。其关键难点不在于简单调用某个蛋白质模型，而在于把工具选择、候选解释、人工确认、运行时证据更新、失败恢复和审计追踪组织成一个可执行且可验证的整体。

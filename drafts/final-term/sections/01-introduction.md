## 1.1 蛋白质计算设计的工程化挑战

蛋白质是生命活动的核心执行者，其功能由三维结构决定，而三维结构又由氨基酸序列编码。de novo 蛋白质设计——即不依赖天然蛋白模板、从零开始设计具有目标功能的氨基酸序列——是计算生物学中最具挑战性的问题之一。过去十年间，以 AlphaFold2、ESMFold、ProteinMPNN 和 RFdiffusion 为代表的深度学习方法显著提升了结构预测和序列设计的精度，使蛋白质设计从经验驱动的试错逐步走向数据驱动的计算流程。

然而，单个模型的精度提升并不自动转化为蛋白质设计流程的自动化。一次典型的 de novo 设计任务通常跨越多个阶段：从任务目标的自然语言描述出发，经过候选序列生成、结构预测、质量筛选、目标评分和结果汇总等环节。每个环节依赖不同的计算工具——序列生成工具给出候选空间，结构预测工具提供折叠置信度，质量门控工具过滤不可用结果——但不同工具在输入输出格式、运行成本（从本地毫秒级到远程分钟级）、失败模式和适用边界上差异显著。如果系统仅在任务开始前选定一条工具链并按序执行，一旦中间步骤的结果偏离预期、高代价工具调用失败或质量门禁拒绝大部分候选，系统缺乏有效的应对手段。

更深层的问题在于，蛋白质设计不是一个"给定输入、期望固定输出"的批处理任务。科研人员在设计过程中持续做出判断：这条候选序列值得送入昂贵结构预测吗？当前结果是否暗示工具链的后半段需要调整？这次失败是偶发噪声还是系统性偏离？现有的大多数蛋白质设计平台将这些判断留给了人工——科研人员通过命令行脚本串联工具、手动检查中间文件、根据经验决定下一步——这种模式的效率、可复现性和可审计性在规模化场景下面临显著瓶颈。

因此，蛋白质计算设计面临的挑战不仅来自生物学和算法层面，更来自**软件工程层面**：如何在异构工具之间建立可组合、可执行的工作流？如何在执行过程中根据中间证据动态调整后续步骤？如何在高风险节点引入人工审查而不破坏自动化？如何在失败发生后进行可审计的恢复而非直接丢弃已完成的工作？这些挑战不是任何单一蛋白质模型或 LLM 能单独解决的，它们需要一个系统级的方案。

本文正是从这个工程化缺口出发，设计并实现一个面向 de novo 蛋白质设计的多 Agent 协作与自适应工作流规划系统。

## 1.2 国内外研究现状

### 1.2.1 蛋白质设计工具与平台

蛋白质设计的计算工具在过去十年间经历了从物理力场到深度学习的范式转变。Rosetta 是最早的系统性蛋白质设计平台之一，提供了基于物理能量函数的固定骨架设计和柔性骨架设计能力。随着深度学习的兴起，ProteinMPNN 使用图神经网络从结构反推序列，ESMFold 基于 Transformer 实现快速结构预测，ProtGPT2 以语言模型方式生成类天然序列，RFdiffusion 通过扩散模型实现骨架生成。这些工具显著提升了单步任务的精度和速度。

在平台层面，RosettaScripts 提供了 XML 格式的工作流定义语言，允许用户编排多个 Rosetta 模块的顺序执行。BioPython 为常用生物信息学操作提供了 Python 接口。ColabFold 通过 Jupyter Notebook 环境简化了 AlphaFold2 的使用门槛。然而，这些平台要么限定了固定的工具生态（如 RosettaScripts 只能编排 Rosetta 工具），要么缺乏工作流级的控制能力（如 ColabFold 专注于单次预测），在跨工具的智能编排、运行时决策和失败恢复方面存在明显空白。

### 1.2.2 大语言模型驱动的自动化 Agent

以 GPT-4、Claude 等为代表的大语言模型（LLM）在 2023-2024 年间催生了大量自动化 Agent 研究。ReAct 范式将推理（Thought）和行动（Action）交织在同一个循环中，使 Agent 能够根据环境反馈调整策略。AutoGPT 和 BabyAGI 等项目将任务分解为目标分解-执行-评估的循环。在科学领域，ChemCrow 将 LLM 与化学工具集成，展示了 LLM 在专业领域的工具调用能力。

在蛋白质设计方向，已有工作探索了 LLM 在单步工具选择和序列评估中的应用。但直接将 LLM Agent 应用于多步蛋白质设计工作流时面临几个关键挑战：工具调用的失败率高（尤其在远程服务场景）、长链路下的上下文漂移、人工确认点的缺失、以及决策的不可审计性。这些挑战说明，LLM Agent 范式提供了"自然语言理解 + 工具调用"的能力基础，但需要一个结构化的控制层来保证执行的可靠性——这正是本系统引入 FSM、HITL 和 CEBRA-WP 的出发点。

### 1.2.3 科学工作流的自适应与故障恢复

科学工作流管理是分布式计算和 e-Science 领域的经典问题。Pegasus、Kepler 和 Nextflow 等工作流引擎提供了 DAG 定义、任务调度和重试机制。在故障恢复方面，科学工作流研究已经识别了 retry、alternative resource selection 和 partial re-execution 等恢复策略。但传统科学工作流的恢复大多依赖预定义的故障处理规则，缺乏基于运行时证据的动态决策能力。

在部分可观测和故障可恢复的研究传统中，信念状态（belief-state）是应对不完全可观测环境的经典概念。Kaelbling 等人提出在部分可观测 Markov 决策过程中，应通过显式的信念状态而非瞬时观测直接决策。Shani 强调了在部分可观测规划中启发式函数需要显式考虑随机效应和信息价值。这些理论为本系统的 Lite belief-state 设计提供了原则性依据。

### 1.2.4 人在环路的科学工作流

人在环路（Human-in-the-Loop）在机器学习中被广泛讨论，但在科学工作流领域的研究相对有限。现有的 HITL 实践大多以非结构化方式实现——科研人员通过命令行或日志检查进度，手动决定是否继续或修改——缺乏结构化的决策对象、可审计的决策历史和可恢复的执行上下文。本系统将 PendingAction 和 Decision 建模为一等数据对象，在科学工作流中引入结构化的 HITL 机制，是本课题区别于现有工程的特色之一。

## 1.3 现有方法的局限与本课题的切入点

综合以上研究现状，现有方法在面向高代价蛋白质设计工作流时存在四个核心局限：

**缺乏跨工具的智能规划能力。** 现有平台要么将工具选择留给人（RosettaScripts 的 XML 编排），要么限定在单一工具生态内（ColabFold）。蛋白质设计需要跨多个能力阶段（序列生成、结构预测、质量控制、目标评分）的协同，手动编排在任务数量和工具组合增加时迅速变得不可管理。

**缺乏运行时的自适应调整能力。** 无论是传统科学工作流引擎还是 LLM Agent，大多在任务开始前确定执行路径。一旦执行过程中出现工具失败、质量门禁拒绝、预算超限或安全警告，系统要么回退到人工干预，要么直接失败。缺乏基于运行时证据（失败类型、质量指标、预算消耗、安全信号）动态调整的机制。

**缺少结构化的人机协作边界。** HITL 在科学工作流中的实践大多是非结构化的——科研人员手动检查中间产物、通过经验判断是否继续。这种方式缺乏可审计的决策历史，也无法在系统重启后恢复完整的决策上下文。

**恢复路径与审计链路的薄弱。** 现有系统对失败的处理通常是记录日志后终止或回滚。但在高代价工作流中，一个步骤的失败不应该否定前面所有已完成步骤的价值。保留有效前缀、进行局部修补、只在必要时重规划——这种层次的恢复控制需要事件日志、任务快照和结构化决策对象的配合，而大多数现有系统缺乏这一完整链路。

本课题的切入点正是填补这四重缺口：构建一个以 FSM 为控制骨架、以多 Agent 为职责划分、以 CEBRA-WP 为运行时决策核心的智能工作流系统，在蛋白质设计的工具链组合、运行时调整、人工确认和失败恢复四个维度上提供系统级的解决方案。

## 1.4 论文主要工作

本文围绕上述目标，完成了以下工作：

**（1）设计了一个面向高代价科研工作流的五层架构。** 架构将系统分为输入层、智能规划层、执行层、安全与汇总层和资源层，以 FSM 为控制面 SSOT。四类 Agent（PlannerAgent、ExecutorAgent、SafetyAgent、SummarizerAgent）在明确的职责边界内协作，人工审查通过 PendingAction/Decision 契约嵌入控制流。

**（2）提出了 CEBRA-WP 自适应工作流规划算法。** 算法以 Lite belief-state 为核心，通过静态多目标评分、后验目标评分、信念更新、运行时重排序和恢复动作选择五个阶段，为高代价工作流的 continue/patch/replan/stop 决策提供可解释的信息基础。四种策略组（Static Top-1、Fixed Threshold Gate、Dynamic Recovery、Lite Belief-State）构成可消融的验证框架。

**（3）实现了完整的前后端系统原型。** 后端基于 Python + FastAPI + Pydantic，提供 15 个 API 端点覆盖任务录入、HITL 交互、事件查询和报告读取。前端基于 React + TypeScript + Vite，以 Dashboard、Task Builder、Task Detail 和 Event Timeline 四页面组织操作员工作台。系统采用自定义 Workflow/FSM 控制执行流程，通过 ToolAdapter 统一接入 ESMFold、OpenFold、ProteinMPNN、ProtGPT2 等蛋白质设计工具。

**（4）完成了多层次系统验证和 84-run 策略对照实验。** 系统测试通过 13 个测试用例覆盖 API 合约、FSM 迁移、HITL 边界、快照恢复和安全判定。84-run 四组消融实验验证了 CEBRA-WP 的机制可行性——lite_belief_state 在所有运行中持续产生有效信念状态观测——并揭示了固定门控在缺少运行时重排序时的 patch 循环成本，以及 lite/dynamic 相比 fixed 节省 28.6% 高代价调用的成本控制证据。

## 1.5 论文组织结构

本文共八章，组织结构如下。

**第 1 章 绪论**。介绍蛋白质计算设计的工程化挑战、国内外研究现状、现有方法的局限、本课题的切入点和论文的主要工作。

**第 2 章 相关技术与研究工作**。概述 de novo 蛋白质设计的六阶段流程、LLM Agent 协作范式、科学工作流的状态管理与故障恢复、以及蛋白质设计核心工具的原理和适用边界。

**第 3 章 系统需求分析**。从蛋白质设计工作流的实际问题出发，明确系统的用户场景、六类功能需求（任务接入、候选生成、工作流执行、HITL、运行时自适应、审计）和五项非功能需求。

**第 4 章 系统总体设计**。提出五层分层架构，定义四类 Agent 的职责边界，设计包含 11 个状态的 FSM 生命周期模型和六阶段 de novo 能力分层，详细阐述 CEBRA-WP 算法的离线候选生成、在线信念更新、后验评分和恢复动作选择机制，并给出七类模块的设计方案。

**第 5 章 系统实现**。描述技术选型与工程结构、任务接入与后端 API 实现、前端工作台的页面组织、工作流运行时与执行引擎、CEBRA-WP 的工程落点以及工具适配器的实现细节。

**第 6 章 系统测试与验证**。从 API 服务就绪、数据契约、HITL 边界、FSM 迁移、快照恢复、前端/CLI 可用性、失败恢复和安全边界七个维度报告系统功能的验证结果。

**第 7 章 策略对比实验与结果分析**。在 84-run 四组消融矩阵中分析 CEBRA-WP 的机制可行性、静态规划的必要性、信念状态的增量价值和成本控制效果，并通过四个典型案例提供机制洞察。

**第 8 章 总结与展望**。总结论文工作与主要贡献，诚实讨论统计效力、恢复覆盖、外部基线和原型化程度四方面的不足，展望实验规模扩展、恢复层级增强和生产化演进等未来方向。

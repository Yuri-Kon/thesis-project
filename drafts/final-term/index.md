# 毕设论文组织

## 问题

如何在软工专业的固定篇目之间，与我的算法之间作出权衡呢？

## 权衡方式

|部分|软工视角|算法视角|写作策略|
|:---|:-------|:-------|:-------|
|需求分析|系统要解决什么用户问题|为什么普通固定流程不够|以系统需求为主，顺便带出算法需求|
|总体架构|分层架构、模块职责、数据流|CEBRA-WP 位于工作流控制/智能规划层|明确算法在系统中的位置|
|模块设计|UI、API、Agent、工具适配器、存储|Planner、RuntimeState、Recovery 作为核心模块|不要把算法和系统割裂|
|详细设计|FSM、HITL、接口、数据结构|候选生成、可行性过滤、运行时状态更新、动作选择|系统实现和算法实现并列写|
|实现章节|代码模块、接口、数据结构|CEBRA-WP的工程实现|系统实现和算法实现并列写|
|实验章节|系统功能测试、集成测试|算法有效性、消融实验、恢复成功率|两类验证都要有|


## 前半部分算法应该如何出现

最好在需求分析里埋下算法必要性。例如系统需求不只是“能自动执行蛋白质设计流程”，而是：

- 需要根据任务目标自动生成工具链
- 需要在工具生成后动态调整流程
- 需要在高风险步骤前提供人工确认
- 需要根据运行时反馈决定继续、重试、修补、重规划或终止

这些就是 CEBRA-WP 的需求来源。

在总体架构里把 CEBRA-WP 放在核心决策层。架构图可以解释为：

- Web UI / API 是交互入口
- Workflow FSM 是控制骨架
- Multi-Agent 是执行组织方式
- CEBRA-WP 是运行时规划与恢复决策核心
- Tool Adapter 是外部能力接入层

模块结构里保留一个“核心算法模块”，不要只写 PlannerAgent、ExecutorAgent 等，单独抽一个一级模块：

> 自适应工作流规划与恢复模块

它下面可以包含：

- 候选计划生成
- 可行性过滤
- Lite belief-state / RuntimeState 更新
- 运行时动作选择
- patch / replan 触发
- HITL 候选解释

最后在业务流程里标出算法介入点。这样算法自然嵌进系统流程。
